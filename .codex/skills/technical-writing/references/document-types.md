# 문서 유형 선택과 템플릿

## 빠른 선택 질문

- 독자가 처음부터 끝까지 따라 하며 익혀야 하나요? 그러면 학습 중심 문서를 우선 검토하세요.
- 독자가 특정 작업을 수행하거나 오류를 해결해야 하나요? 그러면 문제 해결 문서를 우선 검토하세요.
- 독자가 API, 옵션, 매개변수, 속성 같은 특정 사실을 빨리 확인해야 하나요? 그러면 참조 문서를 우선 검토하세요.
- 독자가 개념, 원리, 배경, 트레이드오프를 깊이 이해해야 하나요? 그러면 설명 문서를 우선 검토하세요.

기술 블로그도 예외가 아닙니다. 블로그라는 형식보다 독자의 목표가 더 중요합니다. 하나의 글 안에 여러 유형이 섞일 수는 있지만, 가장 강한 독자 목적을 기준으로 주 유형을 정하세요.

## 유형별 설계 원칙

### 1. 학습 중심 문서

처음 접하는 독자가 흐름을 따라가며 결과를 만들게 하세요.

- 처음부터 끝까지 순서대로 읽어도 자연스럽게 진행되게 쓰세요.
- 독자가 중간에 막히지 않는 `성공 경로`를 먼저 설계하세요.
- 사전 요구사항이 있으면 초반에 분명하게 밝히세요.
- 학습 문서는 보통 `목표 -> 준비 -> 실습 -> 적용 -> 확장` 순서로 흐름을 잡으면 안정적입니다.
- 단계마다 무엇을 하는지와 왜 하는지를 함께 설명하세요.
- 각 단계가 성공했는지 확인하는 기준을 함께 제시하세요.
- 마지막에는 성공적으로 끝났을 때 보이는 결과를 확인하게 하세요.
- 예제 코드는 실제로 실행해 보고, 바로 복사해서 실습할 수 있게 정리하세요.
- 예제는 가능한 한 간단한 것부터 시작해 점진적으로 난이도를 올리세요.
- 핵심 흐름을 흐리지 않는 선에서 FAQ, 자주 발생하는 문제, 추가 예제를 문서 뒤나 접을 수 있는 영역으로 분리하세요.

#### 시작하기와 튜토리얼 구분하기

- `시작하기`: 전체 흐름과 핵심 개념을 빠르게 잡게 하는 문서입니다. 설치, 기본 설정, 필수 개념 소개에 적합합니다.
- `튜토리얼`: 명확한 결과물을 만들게 하는 문서입니다. 단계별 실습과 실행 가능한 코드가 더 중요합니다.

```markdown
# [튜토리얼 제목]

## 목표
[이 글을 마치면 독자가 무엇을 할 수 있는지 설명]

## 사전 요구사항
- [필요한 환경이나 지식]

## 단계별 가이드
### [첫 번째 단계]
[해야 할 일, 예시, 기대 결과]

### [두 번째 단계]
[다음 단계 설명]

## 최종 결과 확인
[완료 상태 확인]
```

### 2. 문제 해결 문서

이미 기본 개념을 아는 독자가 특정 문제를 해결하게 하세요.

- 문제 상황을 초반에 명확하게 정의하세요.
- 문제의 원인과 겉으로 드러난 증상을 구분해서 설명하세요.
- 에러 메시지, 로그, 재현 조건이 있으면 함께 제시하세요.
- 해결 방법은 바로 적용 가능한 행동 단위로 정리하세요.
- 여러 방법이 있으면 선택 기준을 함께 제시하세요.
- 해결책이 왜 동작하는지 원리도 짧게 설명하세요.
- 운영체제, 런타임 버전, 라이브러리 버전 같은 환경 차이를 반영하세요.
- 해결 후 어떤 상태가 정상인지 확인 방법을 제공하세요.
- 에러 코드 설명 문서와 트러블슈팅 문서를 구분하세요.
- `에러 코드 설명 문서`: 에러의 의미를 빠르게 조회하게 하는 문서입니다.
- `트러블슈팅`: 원인 진단과 해결 절차를 제공하는 문서입니다.

#### How-to 가이드와 트러블슈팅 구분하기

- `How-to 가이드`: 특정 작업을 성공적으로 수행하게 하는 문서입니다.
- `트러블슈팅`: 이미 발생한 문제를 진단하고 해결하게 하는 문서입니다.

```markdown
# [문제 해결 문서 제목]

## 문제 정의
[독자가 겪는 문제 상황]

## 사전 요구사항
[필요한 환경이나 조건]

## 해결 방법
### [첫 번째 해결 방법]
[구체적인 조치]

### [두 번째 해결 방법]
[대안이 있다면 추가]

## 해결 후 확인 방법
[정상 동작 확인]
```

### 3. 참조 문서

특정 기능이나 API 정보를 빠르게 찾게 하세요.

- 개요는 짧게 쓰고 바로 핵심 정보로 들어가세요.
- 정보는 정확하고 완전해야 하며 누락이 없어야 합니다.
- 시그니처, 옵션, 반환 값, 예제를 일정한 순서로 배치하세요.
- 표를 쓸 때는 비교 기준을 고정해 스캔하기 쉽게 만드세요.
- API 키, 인증 방식, 요청 헤더처럼 먼저 알아야 할 정보는 초반에 눈에 띄게 배치하세요.
- 목차, 앵커, 주제별 섹션을 활용해 검색과 탐색을 쉽게 만드세요.
- 예제는 실제 사용 맥락이 드러나도록 고르세요.
- 관련 API, 함수, 컴포넌트와의 연결 지점을 안내하세요.
- 제한사항, 주의사항, 전제 조건이 있으면 빠뜨리지 마세요.

```markdown
# [참조 문서 제목]

## 개요
[무엇인지, 언제 쓰는지, 어떤 가치를 주는지]

## 속성 및 옵션
| 이름 | 타입 | 기본값 | 설명 |
|------|------|--------|------|
| ...  | ...  | ...    | ...  |

## 시그니처
[예제 코드]

## 반환 값
[반환 값 설명]

## 사용 예제
[구체적인 사용 상황과 예제]
```

### 4. 설명 문서

개념과 배경을 이해하게 하세요.

- 이 개념이 무엇인지 먼저 정의하세요.
- 왜 등장했는지와 어떤 문제를 해결하는지 설명하세요.
- 다른 접근 방식과 비교하고 장단점이나 트레이드오프를 설명하세요.
- 필요한 선행 지식이 있으면 초반에 안내하세요.
- 실제 활용 장면이나 판단 기준까지 연결하세요.
- 실제 사용 사례나 응용 방법을 함께 보여주세요.
- 절차보다 이해를 우선해야 하므로 배경 설명을 충분히 제공하세요.
- 복잡한 개념은 다이어그램, 흐름도, 표처럼 시각 자료를 활용해 설명하세요.
- 서비스나 산업 맥락을 다루는 도메인 문서도 설명 문서로 볼 수 있습니다.

```markdown
# [개념명]

## 개념 소개
[개념 정의]

## 등장 배경
[왜 필요한지, 어떤 문제를 해결하는지]

## 활용
[실제 사용 맥락]
```

## 블로그 글에 적용하는 법

- 기능 소개 글인데 따라 하기 흐름이 핵심이면 학습 중심 문서로 쓰세요.
- 특정 구현 방법을 알려주는 글이면 문제 해결 문서로 쓰세요.
- 옵션, 속성, API 차이를 정리하는 글이면 참조 문서로 쓰세요.
- 설계 배경, 원리, 트레이드오프를 설명하는 글이면 설명 문서로 쓰세요.
- 한 글에서 여러 유형을 섞을 때도 서론과 제목은 주 유형에 맞추세요.
- 프로젝트 구현기는 보통 `설명 문서 + How-to 가이드` 조합이 잘 맞습니다.
- 라이브러리 소개 글은 `학습 문서 + 참조 문서` 조합이 잘 맞습니다.
