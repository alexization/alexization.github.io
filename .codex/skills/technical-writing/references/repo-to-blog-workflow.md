# 초안과 프로젝트 저장소를 기술 블로그 글로 바꾸는 워크플로

## 목적

사용자가 `초안`, `메모`, `기획 의도`, `프로젝트 저장소`를 함께 주면, 저장소에 근거한 사실과 초안의 서술 의도를 결합해 완성도 높은 기술 블로그 글을 만드세요. 초안의 문장보다 저장소의 실제 구현이 더 신뢰할 수 있는 근거입니다.

## 1. 입력 우선순위 정하기

- 저장소: 사실 확인의 기준입니다.
- 초안: 문제의식, 강조점, 저자의 말투를 파악하는 재료입니다.
- 사용자 요청: 최종 산출물의 형식과 범위를 결정합니다.

초안에 있는 주장이라도 저장소에서 확인되지 않으면 그대로 단정하지 마세요. 저장소에 없는 배경이나 의도는 추정이 아니라 가정으로 처리하세요.

## 2. 저장소를 빠르게 훑는 순서

가능하면 다음 순서로 읽으세요.

1. `README`, `docs/`, 발표 자료, 기존 블로그 초안
2. `package.json`, 빌드 설정, 실행 스크립트, 의존성
3. 진입점, 주요 모듈, 핵심 도메인 로직
4. 예제 코드, 테스트, 샘플 데이터
5. 에러 처리, 설정 파일, 제한 사항이 드러나는 부분

확인해야 할 질문:

- 이 프로젝트는 어떤 문제를 해결하나요?
- 누가 왜 이 프로젝트를 사용하나요?
- 핵심 기능은 무엇인가요?
- 구현에서 특별한 선택이나 트레이드오프가 있나요?
- 독자가 관심 가질 만한 코드 근거는 어디에 있나요?
- 실제 사용 흐름을 보여주는 파일은 무엇인가요?

## 3. 글의 기본 유형 정하기

- 사용법을 따라 하게 하려면 `학습 문서`를 기본형으로 잡으세요.
- 특정 구현 방법이나 개선 과정을 설명하면 `How-to 가이드`를 기본형으로 잡으세요.
- 설계 배경과 구조적 판단이 핵심이면 `설명 문서`를 기본형으로 잡으세요.
- API나 옵션 자체가 중심이면 `참조 문서`를 기본형으로 잡으세요.

프로젝트 구현기는 대개 다음 조합이 가장 자연스럽습니다.

- `설명 문서 + How-to 가이드`
- `학습 문서 + 설명 문서`

## 4. 초안 진단하기

초안을 읽고 다음을 분리해서 판단하세요.

- 유지할 것: 문제의식, 핵심 주장, 경험적 통찰, 말투
- 고칠 것: 구조 혼선, 과장, 저장소와 맞지 않는 설명, 독자 목표와 안 맞는 장황함
- 보강할 것: 배경, 정의, 코드 근거, 예제, 결과, 한계

초안이 거칠어도 바로 문장부터 고치지 마세요. 먼저 유형과 구조를 바로잡은 뒤 문장을 다듬으세요.

## 5. 추천 글 구조

프로젝트 기반 기술 블로그 글은 보통 아래 구조가 안정적입니다.

```markdown
# 제목

짧은 개요

## 문제
[무엇이 불편했고 왜 풀어야 했는지]

## 해결 아이디어
[어떤 접근을 택했는지]

## 구현
[핵심 구조, 코드 근거, 데이터 흐름, 중요한 파일]

## 사용 방법 또는 적용 결과
[독자가 바로 써볼 수 있는 예시 또는 적용 효과]

## 트레이드오프와 한계
[무엇을 포기했고 어떤 조건에서 주의해야 하는지]

## 다음 단계
[확장 아이디어, 관련 글, 참고 문서]
```

튜토리얼에 가까우면 `문제`보다 `목표`와 `준비사항`을 앞에 두세요.

## 6. 코드와 예시를 고르는 기준

- 저장소에 실제로 존재하는 코드만 예시로 쓰세요.
- 핵심 아이디어를 드러내는 최소 단위 코드만 가져오세요.
- 코드가 길면 전체를 싣지 말고 핵심 부분만 설명하세요.
- 파일 경로, 함수 이름, 설정 키, 명령어는 저장소 표기를 그대로 따르세요.
- 예시는 독자가 무엇을 보고 이해해야 하는지 한 줄로 먼저 설명한 뒤 제시하세요.

## 7. 사실 검증 체크리스트

- 명령어가 실제 스크립트와 맞나요?
- 파일 경로와 모듈 이름이 저장소와 맞나요?
- 기능 설명이 코드 동작과 맞나요?
- 버전, 옵션, 환경 요구사항이 저장소와 맞나요?
- 장점만 쓰고 한계나 조건을 숨기지 않았나요?

## 8. 최종 산출물 원칙

- 독자가 얻는 가치를 도입부에서 바로 보여주세요.
- 초안의 개인적인 경험은 살리되, 저장소 근거가 없는 표현은 줄이세요.
- 구현 세부 사항은 독자가 이해할 만큼만 설명하고, 코드와 구조의 연결을 분명히 하세요.
- 기존 초안을 고쳐서 완성하는 작업이라면 `무엇이 문제였는지`, `어떻게 구조를 바꿨는지`, `최종 글이 어떻게 달라졌는지`가 드러나게 정리하세요.
- 필요하면 글 끝에 FAQ, 참고 링크, 관련 파일 경로를 덧붙이세요.
